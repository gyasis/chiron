Chapter 1 / 6

The two-axis insight

Knowledge-graph systems collapse easily in your head: "it's where I save things." But Graphiti — like every memory backend worth using — has at least two independent coordinates. Conflate them and you'll either over-share data across contexts or starve a query you should have been able to answer.

Axis 1 — namespace

group_ids
Tenant / partition / "which world"
  • Lets you ask: "answer only from this world."
  • You write once to a group; every query must declare which group(s).
  • Today: one value — developer_gyasisutton.

Axis 2 — domain

entity_types
What kind of thing is this
  • Lets you ask: "what's my workflow for X" not "anything about X."
  • Five categories only. Hard-defined, not free-text.
  • This is where your real domain modelling lives.
Axis 1 is "which world." Axis 2 is "what shape." The mistake was treating "domain" as a synonym for "world." It isn't. Your domains are entity-types; your worlds are group_ids.
Chapter 2 / 6

Axis 1 — group_ids: the namespace

A group_id is a data partition. Two episodes in two different groups are invisible to each other unless a query explicitly names both groups. Think tenant. Think Postgres schema. Think Notion workspace.

Your current state

$ mcp__graphiti__search_nodes(
    query="...",
    group_ids=["developer_gyasisutton"],   # one tenant only
    max_nodes=5
)

You have a single namespace: developer_gyasisutton. Everything universal you've ever recorded lives in there together. That's been fine for the <30 episodes rule because at that size, partitioning would be over-engineering.

What you could do with more namespaces

hh_dev_teamHH-only governance: dbt/Cube/Zeno rules, MDM joins, AP-010 zombie patternsHH-specific work doesn't need to influence personal projects

Important caveat Multiple group_ids only earn their keep when queries get tighter. If 95% of your queries hit "all groups," you've just paid the partition tax without the benefit. Don't split until a query actually needs the cut.
Chapter 3 / 6

Axis 2 — entity_types: the five categories

This is your real "domain" axis. Inside one group_id, every episode carries a type that says what kind of knowledge it is. Your rules/tools/graphiti.md nails it down to exactly five — no improvisation, no twelfth category for "stuff."

Preference

How you want things done. Coding style, tool choices, interaction style.

"Preference: ANSI SQL for Snowflake+Databricks"

Workflow

Reusable multi-step processes. Setup patterns. Deployment recipes.

"Workflow: CREATE VIEW → GRANT SELECT → appears in Databricks"

ToolPattern

Proven command/API call sequences. The "do X, then Y" patterns.

"ToolPattern: Superset auth → API call → verify result"

Recipe

Documented fix patterns. Each one points at a file under ~/.claude/recipes/.

"Recipe: Superset params must be JSON string. Path: ~/.claude/recipes/superset-params-json-string.md"

Finding

Atomic recurring facts: IDs, connection strings, auth tokens, project keys.

"Finding: Atlassian cloud ID is e29377f4-..."

How to query a single type

mcp__graphiti__search_nodes(
    query="how do I ship to Databricks",
    group_ids=["developer_gyasisutton"],
    entity_types=["Workflow"],     # the underused axis
    max_nodes=5
)

This is the lever most people miss. Searching with no entity_types filter means every preference, finding, and one-off ToolPattern competes for relevance. Searching just for Workflows narrows the noise to "the multi-step processes you've blessed."

group_ids partition the universe. entity_types shape the question.
Chapter 4 / 6

What you have right now

Current state of your Graphiti:

  • 1 group_id — developer_gyasisutton.
  • 5 allowed entity_types — the catalog above.
  • Hard cap < 30 episodes total — soft constitution from rules/tools/graphiti.md.
  • Admission test (BLOCKING): Universal? Low-churn? Behavioral? All three YES, else file memory only.
  • Read protocol: max 2 search_nodes + 1 search_memory_facts per message (cost guard).
  • Conflict resolution: File memory always wins over Graphiti in the current session.

The forces that shape this design

ConstraintConsequence
Each write costs an LLM extraction callDon't write fragments; consolidate before saving
Each read is paid query-time (~1s, modest tokens)Cheap relative to L2 HybridRAG; still rate-limited
Deletion is hard — node ids matterQuality over quantity; /memory-reconcile monthly
The $5K HybridRAG incident (2026-04-20)Economy-first principle applies to L3 too: dedupe first, write second
Why this works You've kept Graphiti small enough that the model can hold the whole graph as a mental cache. That's the point — it's an ID card, not a library. The library job belongs to L2 (HybridRAG).
Chapter 5 / 6

What's possible

You've been using one axis (entity_types) cleanly and ignoring the other (group_ids). Here are the moves that open up once you treat them as orthogonal.

Move 1 — Per-domain namespacing

Spin up hh_dev_team as a second group_id. Migrate HH-only Workflows/Recipes/Findings there. Queries from inside HH work pass group_ids=["developer_gyasisutton", "hh_dev_team"]; queries from personal projects pass only the first. Personal projects no longer pick up "how to scaffold a Cube view" as relevant context.

Move 2 — Multi-tenant simulation

Use group_ids for roles: role_pm, role_oncall, role_engineer. Switch personas by switching the group_id passed to search_nodes. Same brain, different lens. Useful when writing different kinds of doc.

Move 3 — Entity-type-only queries for routine work

Build slash skills that bind to a single entity_type. /find-workflow only searches entity_types=["Workflow"]. /find-recipe only searches ["Recipe"]. Lower noise, faster convergence.

Move 4 — Promotion pipelines

Pair group_ids with the admission test to make promotion explicit. New patterns start in sio_pipeline (the holding tank), and only graduate to developer_gyasisutton when they pass Universal + Low-churn + Behavioral. The graph becomes a quality-controlled pipeline, not a dumping ground.

Move 5 — Audit + reconcile by axis

Run /memory-reconcile with axis filters. Audit just Workflows quarterly (they decay fastest), just Findings annually (they barely change), and just the smallest group_id whenever you suspect partition rot.

Move 6 — Sharing without leakage

If you ever ship a "Gyasi's setup" capability bundle to a teammate, you only export their relevant group_id. developer_gyasisutton stays private. hh_dev_team can ship if they're also on the HH stack. This is how Graphiti pays you back at transfer time.

Chapter 6 / 6

Four stories

Story 1 · Tuesday morning · HH dev session

The Cube measure you "remember solving"

You sit down to fix a Cube measure failing in CI. You vaguely recall debugging this exact failure six weeks ago. With only one group_id and no entity-type filter, search_nodes(query="cube measure failing") returns four preferences, two findings, one workflow — half of them about unrelated Snowflake work. With entity_types=["Workflow", "Recipe"], you get the one Recipe that matters in the first two results. You apply the fix in under three minutes.

Lever: entity_types filter. Cost: zero. Saves: ten minutes.

Story 2 · Onboarding a new laptop

The portable identity, the local quirks

You set up a new MacBook. The cross-machine DNA — developer_gyasisutton — restores via ab compose --capability claude-config-maintainer. But the laptop also needs to know "which paths exist on THIS machine?" — your local Bitbucket clones, the Fusion venv, the ZENO_DIR drift workaround. Those are onboarding_machine_macbook2026. They never pollute your other machine's queries. When the laptop dies, only that group disappears.

Lever: group_ids as locality. Cost: one extra arg per query. Saves: ambient cross-machine confusion.

Story 3 · A six-month-old preference resurfaces

The drift detector

An SIO-mined pattern says "agent keeps suggesting gpt-4o as default." You check Graphiti: there's a Preference from January saying gpt-4o-mini is the floor. The drift is real. Because you partitioned by entity_type, you can query entity_types=["Preference"] alone — five rows — and spot the conflict in two seconds. You enrich (not duplicate) the existing node with the 2026-05-08 incident reasoning. Graph stays at < 30 episodes. No new node added.

Lever: entity_types as audit lens. Cost: one targeted query. Saves: silent rule decay.

Story 4 · Sharing a capability with a teammate

Public DNA, private DNA

A teammate asks for your dbt-Cube setup. You don't want to hand over the contents of developer_gyasisutton — that's your interaction style, your unrelated personal preferences, your home-network paths. But hh_dev_team is fair game: those are team Workflows and Recipes. You export only that group. They ingest it under their own developer_*. group_ids gave you a clean cut between "me" and "us" without inventing a new system.

Lever: group_ids as sharing boundary. Cost: maintaining one extra group. Saves: an awkward "let me sanitize this" review.

What NOT to do Don't shred your one group into eight tiny groups before you have queries that need the cut. Partitioning is forever — un-partitioning is a manual data migration. Walk before you fork.
Today you have a 5-category, single-tenant graph. The leverage isn't to "add more" — it's to use the second axis you already have.
