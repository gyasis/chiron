## Headline finding (the thing that decides the verdict)

**The lessons were already generated by a decomposed, parametrized, stage-by-stage process — one subagent per stage/chapter — not by a free-form agent improvising.** The richest medicine build (`750627eb`, Blood Chemistry, 6 chapters) ran literally as:

```
[subagent] Execute Stages 1–2 of the chiron pipeline … Blood Chemistry      → brief.json + syllabus.json
[subagent] Execute Stage 4 (chapter-write + widgets + QUEST-AI verify) CH1   → chapter1.json
[subagent] … CH2 … CH4 … CH5 … CH6                                           → chapterN.json  (one per chapter)
[subagent] Execute Stage 5 (Assemble) … Sarcoma of the Chest                 → lesson.html + .chiron-state.db
[subagent] Bake per-chapter Listen-mode audio                                → audio/ + manifest
[subagent] URGENT clinical-safety fix … Gemini QC caught hypo/hyper collapse → edit audio-scripts.json + re-bake
```

Each of those Task-prompts is, in effect, **a chain-step spec that already exists**. That makes the deterministic spine of medicine generation **highly chainable**. The genuinely open-ended work is confined to two seams (grounded chapter authoring + QUEST-AI verify). → **Verdict points to (C) Hybrid** (see D5).

## D1 — Per-domain generation step-map (the recipe)

`lib/pipeline.ts` is explicit (`// Per Q8: text-LLM stages 1-4 hand control to the parent Claude Code agent … No SDK call is made here.`). Stages 1–4 **emit a prompt template + slots + an `expectedResponsePath`**; the parent agent fills it and writes the JSON; the deterministic tail (5/6) is already out-of-process scripts. So the "recipe" is the same skeleton for every domain, differing in (a) which `04*` widget prompts fire, (b) grounding corpus, (c) whether a fixed curriculum or the source drives the chapters, (d) the medicine-only QUEST-AI verifier.

### Medicine-only insert (between/within Stage 4) — the QUEST-AI verifier
`prompts/medicine-only/verifier-stage{1,2,3}-*.md`, driven by the `runVerifierLoop` state machine (`pipeline.ts:597`). Stage1 generate → Stage2 verify (every clinical claim supported from source) → Stage3 refine; `MAX_VERIFIER_ATTEMPTS=3` (**LOOP #3**). Two programmatic guards: `assertVerifierStage3SourceSpans` (every corrected/replaced claim's `sourceSpan` must be a verbatim substring of the source) and `assertVerifierStage2NotRubberStamping` (≥5 claims all "verified" ⇒ reject + re-run hotter). **This is the pedagogical heart of medicine and is NOT mechanizable away — it is exactly an `AgenticStepProcessor` + `enable_cove` seam.**

### D1 §B — Per-domain PEDAGOGY (from the prompt bodies — what a chain must PRESERVE)

The plan vs fill split is explicit in the prompts: **Stage-2 syllabus IS the plan** — it emits each chapter's `widgets[]` array + a **150–400-word narrative arc** ("high-level only, NOT the chapter body"); Stage-4 only *realizes* each typed widget. So "big model plans, small models fill piecemeal" is the existing contract, and **widget-mix is a PLAN-time decision** (answers the Gemini Q3: per-syllabus, by the planner, not payload/fixed).

- **Chain 1 — Medical (AMBOSS).** `04c-quiz-clinical-vignette` calls itself "the heaviest pedagogical lift" — a full USMLE/AMBOSS case: scenario stem + labs + leading question + **5 options + per-distractor explanation** + `keyInfo[]` pearls + **Hammer** difficulty + **Dr. Reyes attending tip**, across an **8-category vignette taxonomy** (classic/atypical/pediatric/elderly/immunocompromised/pregnancy/comorbidity/mimicker). "Generate as if it WILL be verified — don't guess, ground everything." Then the **QUEST-AI verifier = a skeptical attending physician**, **source-only by default** (secondary guidelines only if `guidelinesAllowed`), verdict approve/refine/reject. **Mode = accuracy-first, grounded clinical reasoning.** *Preserve:* the vignette anatomy, the taxonomy spread, and the verifier — these are non-negotiable and are exactly the AgenticStepProcessor+CoVe seam.
- **Chains 2/3 — Wards + Medical-language Italian.** `04t-passage-breakdown` (and the ward/dialogue prompts): **source-driven** ("the passage IS the syllabus"), **interlinear** breakdown assuming a **BASIC learner, zero grammar — every function word explained** (clitics, prepositions, verb-phrase pieces). **Lucrezia persona** with **bilingual code-switch** (English instruction, *perfect* Italian targets), greets `{{learnerName}}`, **learner's own turns never voiced**; clinical foundation kept **light** (R-CH3b). **Mode = comprehensible-input, scaffolded from authentic source; language-primary, clinically accurate.** *Preserve:* the interlinear depth, the code-switch register, light-foundation, no-voice-on-learner-turns.
- **Chain 4 — Pure Italian.** Same `04t`/grammar pedagogy but **no clinical layer** — authentic Lucrezia video as the source/curriculum, teach HER examples/distinctions verbatim with a credit line. **Mode = engagement-first comprehensible input.**
- **Cross-cutting pedagogy (all chains):** `04q-match-madness` = the **spaced-retrieval anchor** (timed 2×5 grids; sets per content-type; a final super-set drawing ALL prior) — the return-to revision surface. `04s-lecture-script` = the **audio "TEACH don't read"** rule: every spoken line is net-new teaching, never narration of the visible text; this is how the always-on **foundations layer** (R-CH3b) is delivered as audio.

**Implication for the four chains:** the *pedagogical mode* (accuracy-first vs comprehensible-input) and the *mandatory widgets/verifier* differ enough that a single parametrized chain would blur them — which is exactly why four distinct prompt-chains (D4b) is the right factoring, not one with flags.

**Step counts (medicine, the heavy one):** Stage1-2 (1 step) + Stage3 validate (1, ×≤3 on retry) + Stage4 (**N chapters × ~1 authoring step each, each containing a ≤3-iteration QUEST-AI sub-loop and 1–5 grounding tool calls**) + Stage5 assemble (1) + Stage6 bake (1) + Stage7 QC (×≤3). For a 6-chapter lesson that is **~10–12 top-level steps and 30–60 LLM/tool calls** end-to-end. Language lessons are far lighter (1 grounded author step + assemble + bake).

**Lesson→session map (22 real lessons; rest are `queued:` placeholders in the library index):**

- `68f349c8` (chiron) → klinefelter ×2. 416 calls · assemble/build 28 · 10 AskUserQuestion · packaging-heavy.

**How lessons were really made (two patterns observed):**
1. **Medicine (proper path) = decomposed pipeline over subagents.** "Execute Stages 1-2" → "Execute Stage 4 … CHAPTER k" (one per chapter) → "Execute Stage 5 (Assemble)" → "Bake" → "audio-QC fix". This is the documented pipeline, fanned out. **The agent step-processing IS already a chain.**
2. **Language / medical-Italian (as-built) = monolithic "Author ONE self-contained lesson HTML" subagent** mirroring `LANGUAGE-SKELETON.md` + a reference exemplar (diabete-tipo-2), and in places **chunked `Append to lesson.html`** writes. This is the path **R-CH-PIPELINE explicitly flags as the antipattern** (hand-written HTML → 0 audio widgets / wrong shell). The investigation treats the *medicine decomposition* as the parity target and recommends language be brought onto the same data→assemble spine (it currently isn't).

**The loops (the "short looping" the user asked us to surface):**
| # | Loop | Trigger | Bound | Where |
|---|---|---|---|---|
| 1 | **Validator retry** | Stage-3 Zod/DAG/rubric fail | ≤3 (`MAX_VALIDATOR_RETRIES`) | `pipeline.stage3Retry` |
| 2 | **Per-chapter fan-out** | N chapters | N (one subagent/chapter) | Stage-4 |
| 3 | **QUEST-AI verifier** | unsupported clinical claim | ≤3 (`MAX_VERIFIER_ATTEMPTS`) + rubber-stamp guard | medicine-only `runVerifierLoop` |

**Time/cost hotspots:** (a) **audio bake** dominates wall-clock (107 bake calls in `750627eb`; serialized through one OmniVoice on the Mac); (b) **per-chapter authoring + QUEST-AI verify** dominates LLM cost (135 gemini_research refs, 130 verifier refs); (c) grounding pulls (`harrison-search`) are cheap RAG calls. The audio bake is already off-box (Atelier) and **engine-independent** — it stays a deterministic tail regardless of A/B/C.

## D3 — Job-payload schema + decision-point retirement map

**Key empirical result for unattended feasibility:** I extracted **every `AskUserQuestion`** in the three mega-sessions. The overwhelming majority were **one-time INFRASTRUCTURE/DELIVERY decisions, now settled and codified in rules** — *not* per-lesson content decisions:

| Asked-about (sample) | Class | Status |
|---|---|---|
| TTS provider, Audio scope/granularity/coupling/arch, "when does audio get made" | infra | **settled** → Atelier OmniVoice, per-chapter clips, manifest survives regen (R-CH1) |
| PWA host, one-tap delivery, `.chiron` packaging, icon/app-theme/color, mobile tables, hold-scroll | infra/cosmetic | **settled** → `.chiron` bundle + player |
| Persona/pack location, phrase voice | infra | **settled** → `~/.chiron/`, voice registry |
| **Lesson topic / "what should the lesson cover"** | **content** | → payload `subject` |
| **Lesson source / grounding** | **content** | → payload `grounding` |
| **Med-lang foundations: how handled** | **content (settled as a rule)** | → R-CH3b (light ~2-3 sentences); payload `foundations_depth` default |
| **Lecture-script: "what does the tutor voice say"** | **content** | → derived from chapter exposition; payload `voice/persona` |

**Conclusion:** the *content* decisions an unattended job must pre-answer are a **small, parametrizable set**. Everything else the human was asked is already a global default. This is the strongest evidence that off-site generation is feasible.

### Job-payload schema (minimal fully-specified input)
```jsonc
{
  "subject": "Blood Chemistry — Derangements & Their Acute Presentations", // retires [Lesson topic]
  "domain": "medicine",              // medicine | medical-italian | language-it | research-paper | code
  "sub_mode": "amboss",              // amboss|uptodate | grammar|vocab|passage | …  → curriculum file
  "scope": { "chapter_count": 6, "level": "step-2-ck", "depth": "standard" }, // retires scope-dial
  "grounding": {                     // retires [Lesson source] + grounding-pick — NOW EXPLICIT TOOL STEPS
     "primary": "harrison",          // harrison | paces | mcq | source-file | youtube
     "source_path": "…/source/blood-chemistry-source.md",
     "allow_supplement": ["gemini_research"],   // NEVER deep-research (FR-029)
     "foundations_depth": "full"     // full (medicine) | light (medical-italian, R-CH3b)
  },
  "persona": { "id": "pauls_tutor", "voice_lang": "en" }, // retires [Lecture script]/[Phrase voice]
  "audio": { "bake": true, "loudness_lufs": -20 },        // retires audio Q's (settled defaults)
  "on_fail": "review_queue",         // retires "what does FAILED do with no human" (see D5/§6.5)
  "output_dir": "~/Documents/generated/chiron-<slug>"
}
```
Every field maps to a decision-point it removes (right-column above). Auto-default rules: `sub_mode`→domain default; `foundations_depth`→domain (full/medicine, light/medical-italian); `grounding.primary`→domain (harrison/medicine, paces/medical-italian); `chapter_count`→curriculum or 6.

## D4 — PromptChain feasibility verdict + draft chain (medicine exemplar)

**Verdict: FEASIBLE as a HYBRID chain** (deterministic spine + 2 agentic seams). Exemplar = `chiron-blood-chemistry-amboss` (6 ch). `/promptchain` consulted; draft skeleton at `scratchpad/D4_medicine_chain_skeleton.py` (NOT wired — scope §8). Mapping:

| Real agent step | PromptChain construct |
|---|---|
| Stage 1-2 brief+syllabus (grounds gaps via harrison) | `AgenticStepProcessor` (tool-calling model, harrison/corpus tools) → brief.json+syllabus.json |
| Stage 3 validate (Zod+DAG+rubric = `validator.ts`) | **Python function step** (deterministic) wrapped in `ExternalLoop(max_iters=3)` refine-until-valid → re-runs Stage 2 with issues (**LOOP #1**) |
| Stage 4 per chapter | `ExternalLoop`/`over_worklist` over `syllabus` (**LOOP #2**); each item → a fresh `PromptChain([AgenticStepProcessor])` that writes exposition+widgets, **calls `harrison_search`/`corpus_search` as registered tools**, and runs QUEST-AI via `enable_cove=True` (**LOOP #3 ≤3**) → chapterN.json |
| Stage 5 assemble | Python function step → `assemble.ts`/`build-*-assemble.mjs` |
| Stage 6 bake | Python function step → `bake-lesson-audio.mjs` (Atelier, serialized) |
| Stage 7 audio-QC | `ExternalLoop(max_iters=3, breakers=(qc_clean,))` → Gemini audio-QC → conditional re-bake (**LOOP #4**) |

**Grounding answer (PRD §6.3):** YES — `harrison-search` and the MCQ/PACES corpora can be **plain registered tool steps** (`register_tool_function` + `add_tools([schema])`), because in the real sessions the agent already calls them as bash tools, not via judgment-laden prose. *Picking which* grounding to call is a small per-domain default (D3), not an agent decision. **Models (per user):** authoring/verify seams need a **strong tool-calling model** — `ollama/glm-*-cloud` or Claude (Ollama-Cloud `glm`/Claude); deterministic synthesis/format steps can use a cheaper local model. ⚠ **Risk (recipe §14/§4.14):** tool-weak models hallucinate tool calls — the two agentic seams must use a verified tool-caller; validate GLM-cloud's tool-calling before committing.

**What does NOT chain cleanly (the residual judgment):** the **widget-mix selection per chapter** (which of the 6 medicine widgets fit *this* chapter's teaching point) and the **QUEST-AI refine wording**. Both live *inside* the AgenticStepProcessor objective — acceptable, but they are why this is hybrid, not pure-deterministic (A).

### D4a — How GROUNDING CONTEXT is actually used (retrieve → digest → author → verify)

The retrieved context (Harrison chunks, PACES cases, MCQ items, a PDF, a YouTube transcript) is **never just dumped into the author prompt**. It moves through THREE distinct roles, and only the middle one is where a "bigger model breaks it down":

```
 (1) RETRIEVE            (2) DIGEST / "break it down"          (3) CONSUME
 harrison_search()  ─►   big-context model (Gemini 1M /   ─►  per-chapter AgenticStepProcessor
 corpus_search()        Claude) distills the raw pull        authors exposition+widgets from
 → raw chunks+cites      into a PERSISTED grounding pack      the pack; calls harrison again
 (a TOOL step)           (source/ pack: foundations +         only for on-demand gap-fill
                         per-chapter fact base + VERBATIM            │
                         passages kept for span-checks)              ▼
                                                            (4) VERIFY (QUEST-AI) checks each
                                                            claim's sourceSpan is a verbatim
                                                            substring of the SAME pack
```

- **(1) Retrieval is a plain tool step**, not a model — `harrison_search(query)` / `corpus_search(query)` return chunks+citations. Cheap, deterministic. This is what the real sessions ran as Bash.
- **(2) The "break it down" step is where the big model goes** — and the answer to your question is: **it's a dedicated DIGEST step, not the author step, and its model is chosen for CONTEXT SIZE + reasoning, not tool-calling.** When the pull is large/messy (a whole Harrison disease chapter, many PACES cases), hand the raw corpus to a **long-context model — Gemini (1M) or a Claude (incl. headless YOLO) — to organize it into a chapter-indexed grounding pack** (the "foundations" layer + a per-chapter fact base). In PromptChain this is a **sequential prompt step** (or a light `AgenticStepProcessor` with no tools) whose `model_name` is the big-context model. ⚠ **Critical constraint:** the digest must **preserve verbatim source passages** (keep the original quotes + add an index/summary) — it must NOT paraphrase them away, because the QUEST-AI verifier (Stage-4) requires every claim's `sourceSpan` to be a *verbatim substring* of the pack (`assertVerifierStage3SourceSpans`). So the digest **adds structure, never replaces the source text**.
- **When you DON'T need a separate digest:** if the pull is small (a tight definition, one PACES case), skip step (2) — let the per-chapter `AgenticStepProcessor` call `harrison_search` itself and author directly from the chunks in its own (isolated) loop. The dedicated big-context digest earns its cost only when the retrieved corpus is too big/noisy for the author model's window — which is exactly "send it to one of the bigger models to break it down."
- **(3) Consumption = the per-chapter agentic step** reads the relevant slice of the pack (small, distilled) + the verbatim passages for the claims it makes, and may fire `harrison_search` again for targeted gap-fill. Its internal history is isolated, so the big raw pull never pollutes downstream chapters.
- **(4) Verify** reads the **same persisted pack** — that's why the pack, not the model's memory, is the source of truth.

**So, directly: the grounding context is consumed by the per-chapter `AgenticStepProcessor` (role 3), but when it's large it is first "broken down" by a dedicated long-context DIGEST step on a bigger model (Gemini 1M or Claude/YOLO) into a persisted, span-preserving `source/` pack (role 2). Retrieval itself (role 1) is just a tool call.** This mirrors the existing chiron `source/`-pack pattern and the RAG "tight-chunk index + parent-expand on demand" rule — and it's the same shape for every domain (only the corpus and digest depth change: medicine = full foundations digest from Harrison; medical-italian = a *light* 2-3-sentence digest per R-CH3b).

## D5 — Engine recommendation

**Recommendation: (C) HYBRID — a per-domain PromptChain spine with two bounded agentic seams — built medicine-first.**

**Rationale:**
- The spine (ingest → brief → syllabus → validate → assemble → bake → QC) is **already deterministic / scriptable**; forcing it through a free-form agent (B) re-introduces the non-determinism and infra-question interactivity we want to retire.
- Pure PromptChain (A) can't cleanly own the two genuinely open-ended seams — **grounded chapter authoring** and **QUEST-AI clinical verification** — without an agentic loop; those are exactly `AgenticStepProcessor`. So A collapses into C anyway.
- (B) headless `claude -p --dangerously-skip-permissions` remains the **fallback** for domains not yet ported (and a useful oracle to *generate parity fixtures*), but it can't take input mid-run and reproduces the monolithic-HTML antipattern unless tightly prompted.
- **Per-domain parity (user's goal):** write **one chain per domain** — same skeleton, swap (widget set, grounding tool default, curriculum-vs-source, persona, the medicine-only verifier). Back grounding with **Harrison RAG + MCQ/PACES + GLM/Claude-via-Ollama** as tool/model config — exactly the "easier because per-domain" the user described.

**The seam (where hybrid splits):** deterministic Python/shell for stages 0(text), 3, 5, 6 and the loop scaffolding; `AgenticStepProcessor` (tool-calling model + CoVe) for stage 1-2 grounding and stage 4 chapter authoring+verify. Media ingest (0) stays MCP/whisper tool steps.

**§6 key questions — answered:**
1. **Steps for a medical lesson:** ~10–12 top-level steps, ~30–60 LLM/tool calls (6-ch). Cost hot in chapter-author+verify; wall-clock hot in serialized audio bake.
2. **Deterministic vs judgment:** deterministic = ingest(text)/validate/assemble/bake/QC-scaffold; judgment = chapter authoring + QUEST-AI verify (+ widget-mix pick).
3. **Grounding as tool steps?** YES — registered tools; corpus pick is a per-domain default, not agent judgment.
4. **Engine / seam:** C (hybrid); seam above.
5. **"Failed" with no human:** map to a **review queue, not silent infinite retry** — each loop already has a hard bound (validator ≤3, verifier ≤3 + rubber-stamp guard, QC ≤3). On bound-exhaustion the job writes `status=needs_review` + the structured abort report (`VerifierAbortReport` / validator issues / QC defects) and **stops**; the hub surfaces it. Never ship an unverified medical lesson.

**Fold-back into Hub Phase-2:** the `/generate` job runner = "validate job-payload (D3) → dispatch the domain's hybrid chain (D4) → on success catalog+bundle, on bound-exhaustion → review queue." Bake stays Atelier-serialized regardless of engine.

The four differ only in: prompt set · pedagogical mode · grounding default · widget menu · persona · verify weight. **This is "per-domain parity" made concrete** — four chains, one skeleton.

## D4c — Filling the scaffold WITHOUT a big model "coding the HTML page" (the piecemeal rail)

**The user's hardest constraint, and the prior pain point.** The desired flow — *large model makes the PLAN, then fill the schema piecemeal, then deterministic assembly with no big model coding HTML* — is **already the correct architecture and already exists in code for medicine**; it is simply not generalized and is bypassed by the Italian chains.

**The contract that already exists:**
- `lib/schemas/widget-spec.ts` — a **Zod discriminated union** on `type`, ~35 typed widget variants. Each widget is an independently-validatable JSON object.
- `lib/widget-renderer.ts` — `registerRenderer(kind, fn)` for **every** widget kind; **throws `NotImplemented` on unknown kind** (fails loud, never blank HTML). Open/closed.
- `scripts/build-bloodchem-assemble.mjs` — proof: reads `chapter{n}.json` → `renderWidget(spec)` per widget → writes `lesson.html`. **A model emitted typed JSON; pure code built the page.**

**The piecemeal flow (what each chain does):**
1. **PLAN (big model, once):** syllabus = chapters + per-chapter widget choices + teaching points.
2. **FILL (piecemeal, per chapter/widget; any/local model, parallelizable):** emit **one typed `WidgetSpec` at a time**, Zod-validated. **Never HTML.**
3. **ASSEMBLE (pure code, no model):** `renderWidget` → HTML component per spec; `assemble.ts` injects shell/theme/audio/sqlite.

**Why it has felt like a big model coding HTML (the two real gaps to fix):**
- **(a) The assembler is per-LESSON bespoke** — `build-bloodchem-assemble.mjs` is forked from `build-sarcoma-assemble.mjs` with hand tweaks ("6 vs 5 chapters", "prose field `narrativeHtml` OR `exposition`", "additional widget types"). There is **no single generic data-driven assembler**, so each lesson required code adaptation.
- **(b) Chains 2/3/4 (Italian) BYPASS the rail** — built by an "Author ONE self-contained lesson HTML" subagent (a big model literally coding the page = the R-CH-PIPELINE antipattern → 0-audio/wrong-shell).

**Required to make all four chains headless (the recommendation):**
1. **One generic, data-driven assembler per chain** — reads `syllabus.json`+`chapter*.json` (medicine) / language-skeleton section-data (Italian) + the audio manifest, calls `renderWidget` for every widget, injects the domain shell/theme/audio. Terminal step of every chain = `assemble(domain, dir)` = deterministic. **Retire the per-lesson `build-*-assemble.mjs` forks.**
2. **Put chains 2/3/4 on the SAME data→render rail** — they must emit typed section/widget DATA, not author HTML (the medical-Italian widgets — match-madness, annotated-passage, language-flashcard-deck — are already in the renderer registry).
3. **Structured-output enforcement on the fill** (Zod parse + `instructor`/`outlines` or the model's JSON mode) so `renderWidget` never receives an invalid spec — this is what makes a small/local model safe to fill slots piecemeal.

**Result:** the big model only ever (i) makes the plan and (ii) fills typed slots; **deterministic code assembles the page** — no model writes HTML in any of the four chains. This is the structural answer to "fill the scaffold correctly, piecemeal, without a big model putting the HTML together."

## D4d — Composition: nested / external / internal chains + Claude-as-a-function (raises feasibility)

PromptChain composition is deep, not flat — which means **every genuinely hard sub-part can be its own sub-chain or function step**, so the deterministic spine never has to "do the hard thing" itself:

- **Function step** = arbitrary Python: shell out to **`harrison-search` CLI**, run the **assemble `.mjs`**, run **`bake-lesson-audio.mjs`**, run the **Zod validator**, or invoke **`claude -p --dangerously-skip-permissions` (headless Claude) as a callable ORACLE "just for the analysis"** of one tricky sub-decision — returning its answer as the step output. This is how option (B) is used *surgically inside* (C): Claude/Gemini are dropped in only where reasoning is genuinely required, not as the whole engine.
- **`AgenticStepProcessor`** = an internal tool-loop step (grounded authoring, QUEST-AI verify).
- **Nested chain** = a step that itself runs a `PromptChain` (e.g. the grounding DIGEST as its own retrieve→organize→span-check sub-chain).
- **`ExternalLoop`** = a deterministic bounded loop wrapping any of the above (per-chapter fan-out; validator retry; audio-QC re-bake).

So a chain can be **arbitrarily long/deep**: `ingest → digest(sub-chain) → plan → ExternalLoop[ per chapter: author(agentic) → verify(agentic/CoVe) → fill widgets(typed) ] → assemble(fn) → bake(fn) → ExternalLoop[ QC → re-bake ]`, and any node that's "too hard for code" becomes a Claude/Gemini **function or sub-chain**. **This raises the feasibility verdict's confidence**: nothing in the pipeline is un-chainable, because the chain can always nest a smarter sub-step for the hard part while the spine stays deterministic, resumable, and HTML-free. The design constraint is not "can it be chained" (it can) but "keep the *spine* deterministic + put the reasoning in well-scoped nested seams."

## D5a — Gemini long-context cross-check + risk register

A skeptical-architect pass (Gemini, over the mined corpus) **endorsed Hybrid for medical safety** but flagged risks a rigid chain would *silently* lose. Folded in:

| Risk | Why it bites | Mitigation (in the chain design) |
|---|---|---|
| **Cross-chapter "mid-lesson drift"** | Per-chapter fan-out (LOOP #2) loses the coherence an agent gets by adjusting CH4 from what it learned writing CH2 → "Frankenstein lessons": each chapter valid, the arc broken. | **Pin the narrative arc + per-chapter teaching points in Stage-2 syllabus** (it already is the plan) AND add a cheap final **coherence pass** that reads all chapters for arc/redundancy before assemble. |
| **Pedagogy MODE mismatch** | Medicine = *accuracy-first* (QUEST-AI); language = *engagement-first* (variety/repetition). A shared spine could enforce medical rigor on a Lucrezia lesson (dry) or language-"fun" on Blood Chemistry (dangerous). | The per-domain chain must encode the domain's **pedagogical mode**, not just its widget set — this is the core reason for *per-domain* chains, not one parametrized chain. |
| **Widget fatigue / wrong widget** | Fixed default → every chapter ends MCQ+flashcard (disengaging); pure payload → user-as-instructional-designer (friction). | **Widget-mix = an agentic decision given a per-domain widget MENU + a BUDGET**, then **Stage-3 validator enforces** the chosen widgets actually support that chapter's teaching point. (Supersedes the simpler "inside the objective" note in D4.) |
| **Local-model (GLM) tool-call hallucination / instruction-thinning** | Local models rubber-stamp the verifier or mis-map grounding to chapter context vs the Claude originals. | (a) **Shadow-scoring**: run lessons through GLM, have Claude grade output against the 22 originals; (b) **negative-constraint list** in the objective (don't skip the verbatim-span check, etc.); (c) **structured-output enforcement** (instructor/outlines) for tool-call + chapterN.json schemas. Keep Claude as fallback for the verify seam until GLM passes shadow-scoring. |
| **No stateful resume** | Unattended job fails at CH5/6 → restart wastes the bake/verify already done. | The job runner must be a **stateful orchestrator** (checkpoint per completed chapterN.json; resume from the failed chapter), not a fire-and-forget script. Pairs with `on_fail: review_queue`. |
| **Style-grounding ignored** | Investigation grounded *content*, not *style* (cram-for-MRCP vs foundational-for-student). | Make **`sub_mode`/curriculum a first-class input to the DIGEST step** (D4a) so the source pack is organized for the intended register, not just the facts. |
| **Video temporal grounding** | Video→lesson needs text↔timestamp segmentation (harder than text→chapter); the monolithic path hid this. | The `language-it`/video chain needs an explicit **video-to-chapter segmentation** step (timestamps from `watch_video`) before Stage-2 — call out as a known gap, not in the medicine-first MVP. |

**Net:** the cross-check did not move the verdict (still **C/Hybrid, medicine-first**) but it sharpens three design rules — per-domain chains carry the *pedagogical mode* (not just widgets); widget-mix is an agentic menu+budget gated by the validator; the runner is a **stateful, resumable orchestrator** with shadow-scored model parity before any local model owns the verify seam.
